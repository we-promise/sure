# Enable Banking consent lifecycle admission

`EnableBankingItem::Lifecycle` now owns legacy configuration updates, authorization start and callback installation, revocation, and disconnect. The item entrypoints and existing browser controller call it. Native readiness remains false; this change does not activate migration or implement native consent renewal.

Every operation pins its original item/family/transport fingerprint, rereads the active administrator and linked financial-account permissions, and holds the original item's exclusive migration permit. Short NOWAIT transactions lock financial accounts, the item, actor/owner rows, sources, links, and current migration control before local writes. Provider HTTP runs outside row transactions. Transitional/native ownership, changed source inventory, replaced consent, revoked account permission, and malformed reserved data refuse publication.

The current attempt lives in the existing encrypted `raw_institution_payload` under `enable_banking_consent_attempt`, with format `enable-banking-consent/v1`. Its exact scalar fields identify the item, family, actor, nonce, operation, issue time, state, transport fingerprint, and the completed attempt's original Sync ID and source-inventory fingerprint. Other institution data is retained. This is one current attempt record, not a full historical journal. It does not store the authorization code. Request logging filters exact `code`, `state`, and `error_description` parameter names; diagnostics contain fixed messages and error class only.

Authorization state is signed, expires after one hour, and binds the exact item, family, actor, and current nonce. Starting another authorization changes the nonce. The callback checks current permissions and commits `claiming` plus `requires_update` before its single-use session POST. A timeout, interruption, installation failure, or changed owner cannot authorize a second POST from that state. The committed marker remains `claiming` or is classified `uncertain`; explicit new authorization is the recovery path. The SDK disables automatic retries and redirects for both consent POSTs and session DELETE.

A successful callback installs the session and validated discovered-account snapshots in one transaction, preserving existing source/link/financial IDs and refusing duplicate source-alias or API-route assignments, then creates one pending item Sync. That exact Sync is enqueued only after the permit is released. If enqueue fails, the installed session, completed receipt, and original pending Sync remain committed. Replaying the still-valid signed callback verifies the original source/link inventory and exact original Sync, then can requeue only that pending, uncancelled, non-stale Sync without another exchange. A completed, changed, cancelled, or missing Sync cannot be replaced by replay. This recovery remains bounded by the one-hour signed state expiry; no separate long-lived recovery UI or remote exactly-once guarantee is supplied.

Disconnect preserves upstream revocation. It first validates and commits local link detachment plus a `disconnect_pending` intent while retaining the original session. A refusal to unlink makes no DELETE. Existing selected/historical source policies or dual native links currently refuse this legacy deletion path. The command commits `revoking`, performs DELETE outside the row transaction, and only a confirmed successful response clears the session and permits physical deletion scheduling. The financial accounts and cached provider sources survive until that scheduling decision. Completed disconnect replay can enqueue deletion again without another DELETE.

A crash before DELETE can resume the committed `disconnect_pending` intent against the same session fingerprint. An unknown DELETE result retains the credential and `revoking`/`uncertain` intent, reports failure, and does not schedule deletion, retry DELETE, or allow a settings/new-authorization operation to silently replace that intent. The SDK treats remote 404 as failure, not proof that this request revoked consent. Explicit upstream reconciliation is still required; no recovery UI for that uncertainty is supplied in this slice. Local financial unlink may already have committed when remote revocation fails, and the browser reports the overall operation incomplete.

`Lifecycle.assert_copyable!` is a no-op for other provider item classes. For Enable Banking it refuses pending legacy authorization IDs and every unresolved attempt, so copy/preparation/cutover cannot silently strand a callback or revoke intent. Completed/revoked/absent attempts merely pass this gate; migration separately proves a usable active session and all original source evidence. `session_valid?` also requires `good`, blocking ordinary legacy acquisition after an uncertain exchange.

Signed account picker/setup/link commands, ownership-aware manual sync routing, native renewal/revocation, and administrative uncertain-revocation reconciliation remain separate work. Existing account picker routes are unchanged. Legacy full-cache fingerprint costs and inherited individual reload bounds remain as described in [legacy admission](enable-banking-legacy-admission.md).

Behavioral coverage includes real committed permits, response/permission changes, single-use replay refusal, atomic installation failure, reserved data preservation, disconnect refusal/failure/resume/replay, and queue failure. Controller tests cover signed-state delegation, administrator gating, sanitized refusals, and absence of duplicate sync dispatch; SDK tests check transport retry/redirect exclusions. These tests are authored but unrun because Ruby/Bundler are unavailable. No migration or real provider operation was executed.
