# Account data provider migration matrix

This is a proposed migration specification, not an implemented migration. It accompanies the [architecture proposal](bank-data-providers.md). The inventory was checked against [the schema](../../db/schema.rb), [provider metadata](../../app/models/provider/metadata.rb), the item/account models, importers and processors. It contains all **23 item/account table pairs** and the **24 offerings** exposed in metadata: Plaid US and EU share one pair. “Bank data” includes brokerage and crypto account ingestion in this document.

Market prices, exchange rates, property valuation, LLM, Stripe, GitHub and SSO providers are separate concepts; they have no bank connection/account table pair to transfer. On-chain network clients remain behind [Onchain::Chains](../../app/models/onchain/chains.rb), rather than becoming separate household bank connections.

Target table names follow the [source/authorization refinement](account-data-and-import-rules.md): `provider_connections`, `external_accounts` and optional `provider_authorizations`. Preserve one legacy item per initial connection. Independently managed session fields may move into mapped authorizations, but combining credential owners/connections is a later migration. New import cleanup rules remain disabled during baseline transfer/parity checks; do not change existing rule types or transaction values as part of a table copy.

The [multiple-source refinement](multi-source-ingestion.md) generalizes batches to `ingestion_batches` and adds source authority and evidence mappings. These do not authorize merging existing financial entries during table transfer. PDF convergence is an additional ingestion track, not another provider table pair in this inventory.

## Common column disposition

Destination names below describe responsibilities in the proposed shared tables. A provider's implementation PR must supply a versioned, explicit source-column-to-destination manifest. Compare the manifest with the actual source schema and fail preflight when a column is unclassified; never silently discard an unfamiliar column. A field may be copied to more than one destination only when that duplication is documented.

| Existing data | Proposed destination and rule |
| --- | --- |
| `*_items.id`, `*_accounts.id`, their class/table names | `provider_migration_mappings`: immutable legacy type + UUID + role → shared UUID mapping. A split item has explicit connection/authorization roles; each source account still has one external-account mapping. Enforce uniqueness per role and target kind. Preserve IDs when possible, resolve cross-table UUID collisions through the map, and preserve original timestamps. |
| Item `family_id`, `name`, `status`, `scheduled_for_deletion`, `pending_account_setup` | Explicit columns on `provider_connections`; distinguish absent source columns from false values. Do not activate connections marked for deletion, require reauthorization for already-invalid credentials, or turn ignored/unlinked source accounts into linked accounts. |
| Provider key, Plaid region, Trading212 environment, custom base URLs | Connection identity/configuration with explicit allowlists. Region and environment are routing inputs, not display labels. Preserve existing setting/environment precedence. Do not copy deployment credentials into every family's connection. |
| Tokens, secrets, certificates, sessions, auth identifiers | Explicit allowlisted encrypted attributes on the appropriate credential owner: installation/family configuration, connection or independently managed authorization/session. Decrypt through the source model and re-encrypt through the target API. Never put them in generic metadata, batch headers, diagnostics or mapping JSON. Honor stronger provider-specific encryption requirements and serialize every consumer of a rotating credential owner. |
| Institution name/id/domain/URL/color, `institution_metadata`, `org_data`, `raw_institution_payload`, attached logo | Compact display/query metadata on the connection or source account; the original institution payload becomes a protected snapshot. Preserve account-level institution overrides. Repoint ActiveStorage attachment ownership using the migration map, preserving attachment/blob IDs and avoiding purge callbacks. Most item classes have logos; do not invent one where absent. |
| Provider account `account_id`, `plaid_id`, `*_account_id`, `balance_id`, composite wallet keys | `external_accounts.external_id` or a documented composite identity/identity alias. These are upstream identifiers, not `accounts.id`. Preserve null IDs without merging rows by name, balance or mask. Explicit provider identities appear below. |
| `name`, `currency`, current/available/cash/reserved balances, account type/subtype/status, limits and masks | Typed `external_accounts` attributes or typed feature details. Use decimal storage at least as precise as the source, preserve null versus zero, date versus timestamp and sign conventions. Provider types remain distinct from the financial `Account#accountable_type`. Sensitive masks, IBANs and account numbers need an explicit encrypted disposition. |
| `sync_start_date`, ignored/ownership/manual-sync flags, holdings support, user balance interpretation options | Explicit connection/account options; preserve account-level overrides and inheritance rather than flattening effective values into permanent copies. |
| `next_cursor`, history boundaries, `last_*_sync`, newest event and nonce values | Separate `provider_sync_checkpoints` by connection, optional source account and stream. Store the actual opaque cursor plus its scope, covered window and authority. `last_synced_at` is often derived from `Sync`, not a persisted item column. Keep successful history and derive the same effective watermark. A nonce is authentication state with atomic monotonic updates, not a transaction cursor. |
| `raw_*_payload`, `extra`, report/instrument snapshots | `ingestion_batches` plus protected payload storage, with provider origin, source column/kind, legacy identity, collection time if known, schema version and integrity digest. Preserve scalar/object/array and null/empty distinctions. Split large transaction arrays into page/record batches only with a reversible manifest. Legacy payloads lacking coverage evidence start with completeness `unknown`, not `complete`. Never infer upstream deletion from an imported empty cache. |
| Unknown nonsecret extension fields | Explicit provider-owned typed details or a versioned, validated namespaced metadata schema. Business identity, searchable lifecycle state and concurrency state do not belong in unstructured catch-all JSON. Secrets always have a credential disposition. |
| `AccountProvider` rows | Preserve row UUIDs and `account_id`; backfill a new `external_account_id` link while legacy polymorphic links continue to work. `holdings.account_provider_id` and `debug_log_entries.account_provider_id` must remain unchanged. Preserve current multi-provider cardinality. |
| Financial `accounts`, `entries`, delegated entryables, holdings, balances, categories, merchants, tags, transfers, statements, goals, account shares | No rebuild or reimport during table transfer. Preserve IDs, amounts/currencies, source/external IDs, ownership/sharing, reconciliation and user locks. Subsequent normalization uses the existing import protection rules. |

There is a critical uniqueness transition: [AccountProvider](../../app/models/account_provider.rb) currently allows one link per `(account_id, provider_type)`. Replacing every polymorphic type with `ExternalAccount` under that existing constraint would reject a financial account linked to two different providers. Add and validate the new provider-qualified constraint before retiring the old one. Plaid US/EU currently use the same `PlaidAccount` type: both must retain `provider_key = "plaid"` on `provider_connections`, `external_accounts` and `account_providers`. Store `region` separately; a UI/registry offering key such as `plaid_eu` is not the relational provider key. This preserves the existing cardinality under unique `(account_id, provider_key)` and keeps the composite foreign keys consistent. A later change to that cardinality would be a separate feature.

[Entry identity](../../db/schema.rb) is unique by `(account_id, source, external_id)`, while holding identity is `(account_id, external_id)`. Keep existing `source` strings and all synthesized external IDs byte-for-byte. A shared-table migration is not a reason to change identity algorithms. [On-chain external IDs](../../app/models/onchain_wallet_account/processor.rb) explicitly embed the legacy source-account UUID; retain an immutable ingestion namespace for that case even when shared UUIDs differ.

## Release sequence and universal gate

Waves below order implementation by differing contract risks, not by installation counts; deployment prevalence is not available in source code. Each provider proceeds independently through preflight → resumable backfill → comparison → a small family cohort → wider cohorts → retirement. Failures pause only the affected connection/provider. Every row's acceptance checks supplement this universal gate:

1. Enumerate every item and source account, including inactive, ignored, unlinked, partially configured and scheduled-for-deletion records. Validate same-family membership through every financial account link. Quarantine ambiguous or cross-family links instead of guessing.
2. Establish one authoritative writer per connection. Legacy sync, credential rotation, linking, unlinking, webhook delivery and deletion must consult the migration control record or share a lock before cutover. Do not issue duplicate upstream requests to compare adapters: replay the same persisted input to a non-writing normalizer. Record unresolved queued job/GlobalID references; retain compatibility dispatch until they drain.
3. Copy in bounded resumable batches; record source version, destination identity, counts and digests. Final reconciliation occurs under the connection lock after old writers drain. Retry without adding financial records, issuing auth grants or firing destroy callbacks.
4. Check complete column coverage, decrypted credential equivalence without logging values, payload equivalence, source-account/link counts, financial IDs, monetary totals per currency, holdings quantities and user state. No sum across currencies is an acceptable reconciliation. Validate actual query behavior, not just row counts.
5. Atomically change routing for one connection. Only the active writer may update checkpoints or rotate credentials. Keep old rows readable during rollback. A post-cutover rollback requires reverse-copying changed connection/account/checkpoint/credential state under the same lock; a flag flip to stale tokens/cursors is insufficient. Where a reverse mapper is not implemented, stop the new writer and repair forward instead of claiming rollback is safe.
6. Repoint `syncs.syncable_type/id` and logo ownership through mappings only when compatibility dispatch is ready. Preserve Sync IDs, parent/child relationships, statistics, cancellation and error history. [Family::Syncer](../../app/models/family/syncer.rb) currently discovers `*_items`; prevent simultaneous scheduling of old and new representations. Preserve `last_synced_at` semantics. Historical logs containing legacy IDs stay readable through the mapping.
7. Observe no unexplained normalization differences, unexpected duplicates, authentication loss, data loss or family-access changes across representative success, partial-response, retry, cancellation and reconnect runs. Then retire legacy writers and eventually source tables in separate reviewed migrations. Do not use `destroy` to retire copied records: Plaid removes upstream items, SimpleFIN runs removal callbacks, SnapTrade revokes OAuth tokens and attachments can be purged.

No production database commands, migrations or provider calls are required merely to publish this specification.

After all waves, regenerate the inventory from source table names and provider metadata; require that every discovered bank integration has a completed manifest and migration status. “All migrated” requires both zero remaining eligible legacy-authoritative connections and an explicit disposition for deferred/conflicted/deleting rows. A provider is not finished merely because its happy-path test connection works.

Keep historical financial IDs, transfer pairings, user entry modifications, exclusions, import locks, locked attributes, reconciled statements, holding security/cost-basis locks and manual account ownership unchanged.
